# Weather Report Project — Advancement Report

## 1. How I Started

At the beginning of this project, I was trying to understand how to use an API with Python.

I chose the Weather Report project because I was interested in studying climate change using real historical weather data.

I started with the Open-Meteo Historical Weather API and tested three locations: Milan, Tunis and a general location in France.

My first objective was simple: connect to the API, request a few days of weather data and organize the results in a Pandas DataFrame.

I initially had some difficulties installing Python libraries. Some `pip` commands did not work in my terminal, so I tried different commands until I managed to install the packages.

I also learned the purpose of the main libraries:

- `openmeteo_requests`: Connecting to the Open-Meteo API.
- `pandas`: Organizing and analyzing data.
- `requests_cache`: Caching API responses.
- `retry_requests`: Retrying requests after temporary errors.

After correcting some mistakes in my code, I successfully retrieved my first weather data.

This was my first important step because I started understanding how data moves from an API into a Python program.

---

## 2. Improving My Project Idea

After the first tests, I realized that comparing a few randomly selected locations would not make the analysis very meaningful.

I wanted to organize my locations using a clear method.

I discovered the Köppen–Geiger climate classification, which divides climates into five major groups.

I decided to select two locations from each group:

| Group | Climate | Locations |
|---|---|---|
| A | Tropical | Kisangani, Darwin |
| B | Dry | Aswan, Ulaanbaatar |
| C | Temperate | Tunis, Milan |
| D | Continental | Moscow, Yellowknife |
| E | Polar | Longyearbyen, South Pole |

This gave me ten locations to study between 1986 and 2025.

I tried to choose locations with different geographical characteristics, even within the same climate group.

My main question became: **Do locations belonging to the same broad climate group experience similar temperature changes?**

I also noted that the South Pole is a research location rather than a city, so its data should be interpreted carefully.

---

## 3. Organizing the Python Code

At first, I entered the latitude and longitude values directly into the API parameters.

This worked for a few locations, but it became difficult to manage when I expanded the project.

I changed the code by creating a list of dictionaries containing each location's name, coordinates and climate group.

Then I used a loop to request the data for the selected locations.

During this step, I practiced using `for`, `zip()`, `append()` and `pd.concat()`.

I also made several mistakes with brackets, commas and the structure of the API response. Correcting these errors helped me understand how the code was organized.

One important error happened when I requested three weather variables from the API but tried to process six variables in Python.

I learned that the requested variables must match the data I extract from the API response.

---

## 4. Choosing the Weather Variables

I first worked with mean temperature, apparent temperature and relative humidity.

Later, I expanded the dataset to six daily weather measurements:

1. Mean temperature.
2. Maximum temperature.
3. Minimum temperature.
4. Apparent temperature.
5. Relative humidity.
6. Sunshine duration.

I also prepared two calculated variables: sunshine duration converted into hours and the difference between apparent and measured air temperature.

At one point, I considered adding wind speed, wind direction and surface pressure to study more relationships between weather variables.

However, I decided to keep the main project focused on temperature evolution, climate comparisons and a smaller exploratory analysis of humidity.

A complete analysis of wind, pressure and atmospheric conditions would require more detailed comparisons.

I also changed my requests from hourly to daily data because daily observations were more suitable for studying forty years of weather without creating an unnecessarily large dataset.

---

## 5. Testing the Ten Locations

Before downloading the complete dataset, I tested the API using seven days of weather data for all ten locations.

I encountered some problems with the structure of the responses and the dates.

For example, some dates appeared as the previous day because of differences between local time and UTC.

After making corrections, the test finally worked.

I obtained a DataFrame with **70 rows and 11 columns**.

I checked the results and found no missing values or duplicate city-date combinations.

This gave me enough confidence to expand the collection period.

---

## 6. Collecting Forty Years of Weather Data

After the short tests, I changed the dates to cover January 1986 through December 2025.

My first attempt was to request the complete dataset, but the request was too large.

To solve this problem, I divided the forty-year period into eight smaller periods of five years for each location.

With ten locations, this meant making **80 API requests**.

The smaller requests worked better, but I encountered another problem: the API rate limits.

At first, I received errors about exceeding the number of requests allowed within a short period.

I introduced a delay using `time.sleep(10)` to reduce the request frequency.

This improved the downloading process, although some executions still stopped because of the API's hourly limit.

I also considered saving each completed batch separately so that a failed execution would not require restarting the entire download.

After several attempts, I managed to collect the complete dataset.

### Final Download Results

The final dataset contains:

- 10 locations.
- 40 years of daily weather data (1986–2025).
- 146,100 observations.
- 11 columns.
- 14,610 daily observations per location.

I combined the downloaded data into one Pandas DataFrame and saved it as `weather_1986_2025.csv`.

During the initial checks, I found no missing values or duplicate city-date combinations.

I also noticed that Excel sometimes displayed the CSV values in one column because of separator settings. I learned that this was a CSV import issue rather than a problem with the Python data.

**What I learned:** Working with historical data requires more than making a successful API request. I also needed to manage request sizes, rate limits, errors and data organization.

## 7. Starting Data Exploration

Once the complete dataset was saved, I decided to separate data collection from data analysis.

I kept the downloading code in `test_api.py` and created `DataExploration.py` for processing the saved CSV.

This was useful because I could test calculations without downloading forty years of data again.

I started by checking the dataset dimensions, data types and descriptive statistics.

I also checked missing values, duplicates, temperature consistency, humidity values, sunshine duration and date coverage.

After verifying the data, I calculated general statistics for each location and annual statistics for each year.

The annual aggregation produced **400 records**, representing ten locations over forty years.

I then calculated linear temperature trends in °C per decade and annual temperature anomalies using 1986–2005 as the reference period.

These results were saved in separate CSV files for the visualization stage.

---

## 8. My First Temperature Graph

I started the visualization stage using Matplotlib.

My first graph was for Milan, showing its annual mean temperature from 1986 to 2025.

I used NumPy to calculate a linear trend and displayed it alongside the annual temperature values.

The graph worked, and I could see how the annual temperatures fluctuated around the general trend.

After this first test, I wanted to make the code reusable for all ten locations rather than creating a separate graph for every city.

I created `temperature_visualizations.py` and used a function to display the selected location's temperature trend.

I also started working on a Git branch named `feature/visualizations` to develop this part without directly changing the main branch.

## 9. Temperature Anomalies

After the temperature trend graphs, I created `anomaly_visualizations.py`.

This script used the annual temperature anomalies already calculated during data exploration.

I organized the locations by climate group so that I could first select a group and then choose one of its two locations.

The graph included a horizontal zero line representing the reference average.

I tested the script with Milan and Longyearbyen, and both graphs worked.

During this step, I learned how to filter a DataFrame and how temperature anomalies help compare changes in locations with very different average temperatures.

---

## 10. Comparing Locations Within Climate Groups

Next, I created `climate_comparison.py`.

The objective was to compare the estimated warming rates of the two selected locations within each climate group.

I used the temperature trend results and Matplotlib to create bar charts.

During testing, I noticed that the first version of the graphs was not specific enough. It was difficult to read the exact values.

I improved the graphs by adding numerical labels above the bars and clearer titles.

I also encountered an indentation error while changing the plotting code. After correcting it, the script worked for all five climate groups.

This analysis helped me notice that locations belonging to the same broad climate group can have different estimated warming rates.

For example, Milan and Tunis belong to Group C, but Milan shows a stronger warming trend.

After finishing the notebook, I reviewed the graphs and improved the written interpretations.

For example, I noticed that Longyearbyen has the strongest estimated warming trend among the selected locations, while Darwin has the weakest.
